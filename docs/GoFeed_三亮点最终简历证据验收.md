### 正式实现、历史构建与候选

- Phase B 文档中的旧 Following 读路径属于当时版本。当前读取 Inbox 及所有已关注作者的 Outbox，保留当前为 Push 的作者在曾经 Pull 时的旧视频。历史单事件探针直接强制事件策略。本次纯策略只通过测试夹具修改阈值，Hybrid 用正式 9,000 / 10,000 / 11,000。
- 点赞正式采用 S3 按视频分区与批量 SQL、A2-1 批量发布标记，保留双 Key 缓存。统一 Key 和静态/计数拆分是候选。800 commands/s 为隔离 Worker 输入，A1 分配 Revision 后由实验发布器投递 RabbitMQ，绕过 HTTP 及正式单 Relay 的吞吐瓶颈。
- 正式 API 池为 16 Open / 8 Idle，Worker 有独立池。回源和重建 SQL 的 Semaphore 每进程 8 执行 / 8 等待，入场最多 20 ms，查询期限 250 ms。关注关系、存在性核验和点赞状态等常态 SQL 走共享池。100 ms Pipeline 与直接 MySQL 是临时对照变体。
- 模块 6 对照为 `c628b0f` 与 `25ea6b5`，新版仍用全量 Feed SQL 预算。1,000 账号、10,000 视频、20,000 关注、100,000 点赞，10 VU、20 秒，各三轮。暖 Latest 有效 RPS 中位数 5,103.37 → 7,029.61。50 作者暖 Following 为 1,935.17 → 926.45。该版本与当前生产配置的历史关系已确定，这些结果不作为最终后端性能提升数字。故障停启执行业务过程已有历史 k6 记录。

## B. Hybrid 综合读写成本

### 执行方式与轮次

在独立 MySQL、Redis、RabbitMQ 上执行，作者粉丝分别为 1,000 和 12,000，低粉作者的粉丝是后者的子集。种子 `20261116` 固定图谱、发布和读取序列。两位作者发布量相同，读取样本在共同关注者与全体粉丝中各抽取一半。三组用同样的视频 ID、时间戳、清理、预热和断言。每轮先发 6 条视频、读两次过门禁，再正式执行 8 发布/96 读取或 48 发布/12 读取。发布走真实 MySQL 事务、正式 Relay 和真实 MQ Fanout，测试每次立即触发 Relay，等候选写完后再执行下一条操作。读取走正式 Service。该串行负载旨在隔离读写成本，同时避免把积压波动归因于策略。

发布事务 P50 到 Publish 返回为止。异步时间从事务返回至最后一批 Redis 候选写完，包含 Relay/MQ/Fanout，结束点早于最终 ACK 及部分 Push 的尾页查询。可见时间是事务返回到共同粉丝的首屏首次观察到新视频，包含实际读探测。读 P95 为进程内 Service 用时，成功读取速率的分母是各次 Service 调用时长之和。没有测发布或读取的网络 HTTP 延迟，也没有测 MQ 积压 P99。逐轮 CSV 另保留包括发布、断言和探测的操作序列速率。读 SQL 仅取测量调用的 GORM Trace，排除独立校验查询。

**次数偏差。** 读多 Pure Push 尝试 4 次。第一次预热时全局时间线写入污染完成计数，未进入计时。第二次完成正式序列后，索引审计误把全局时间线当成异常候选键。后两次通过。按执行前采用的口径将预热门禁失败也计入上限，整套续跑使这一格超出三次上限一次。保留两条有效测量，但下表对该格只使用第 3 次尝试，第 4 次不参与结论。其他五格各 2 次并通过。总计 **14 次尝试、13 次进入正式测量、12 次输出有效值、11 次纳入比较**。测量失败的第 2 次没有导出完整指标。 [尝试台账](perf-evidence/measured/hybrid-attempts.csv) · [有效逐轮数据](perf-evidence/measured/hybrid-rounds.csv)

| 读多 | Pure Pull | 2 | 16 | 912 | 18.33 | 2.51 | 27.92 | 3.59（2.95–4.23） | 381.90 | 3.63 |
| 读多 | Hybrid | 2 | 8,008 | 440,456 | 17.84 | 2.57 | 28.44 | 3.56（3.30–3.81） | 375.87 | 3.63 |

每次读取比较独立 SQL 排序的 ID、游标和 `has_more`。每次发布抽查一名共同粉丝的首位可见性，轮末逐键检查 Redis 索引成员和实际键数量。有效轮均通过。

Hybrid 在两种负载都比 Pure Push 少 **92.3%** 候选写命令。写多场景中既保留了普通作者 Inbox，也把候选键内存从 18,080,000 B 降到 1,401,416 B，提交后写完明显更快。相对 Pure Pull，Hybrid 的写入约多 500 倍，候选索引也更大。两者读 P95 的轮间范围重叠，成功读速率的排名随负载变化。该固定图谱的每个读者只关注一至两位作者，而且正式读取为保证切换历史仍检查所有已关注作者的 Outbox。

当前证据证明了 **用远低于 Pure Push 的成本保留普通作者的 Inbox**。若目标只看写命令与内存，本次结果支持 Pure Pull。在所测业务分布下，没有充分证据认定 Hybrid 整体优于 Pure Pull。三条阈值是可解释的工程配置，实验未搜索最优阈值。

### 正确性与明确缺陷

| 验证项 | 实际证据 |
| --- | --- |
| Inbox/Outbox 混合与重复候选 | `TestFollowingHybridMySQL` 通过，包含同一视频从两个索引返回。本次 B 校验成员集合，C 校验六格首屏。 |
| 同毫秒连续分页 | 已有测试直接检查同毫秒视频分页。本次每格预检使用响应游标连续比较独立 SQL 首三页，核对顺序、游标和 `has_more`。 |
| 阈值切换后的旧视频 | 发布用例验证跨阈值时旧事件保留快照。读侧用例验证当前 Push 作者的旧 Pull Outbox 与新 Inbox 候选合并。 |
| 删除和取消关注 | 已有 Following 用例先缓存实体，再删除视频及取消关注，断言返回排除相应陈旧成员。另有详情与列表失效回归。 |

**复现结果。** 同一作者的四条视频时间相同，独立 MySQL 排序为 `80113, 80112, 80111, 80110`。Redis 缺 `80113`，其余三个去重后正好等于 `limit+1`。真实 MySQL 加测试 Redis 的接口服务第一页返回 `80112, 80111`，第二页返回 `80110`。实现验证这三个候选后提前返回，较新的缺项位于下一游标之前，后续翻页也无法看到。新关注、延迟分发、切换或裁剪造成的索引缺项都可能形成相同形状，线上发生频率未测。 [严格复现测试](../backend/internal/feed/following_evidence_test.go) · [失败输出](perf-evidence/measured/full-index-coverage.txt)

**最小修复。** 缺乏可信覆盖证明时，在满页也检查 MySQL。可探测当前游标下、排在第 `limit+1` 个候选之前、且不属于已验证候选的关注视频。若存在，则走已有受预算保护的整页查询。也可先用完整 MySQL 复核保证正确，再调整读取开销。补充包括缺项恰好影响 `has_more` 的断言，修复后复跑该测试，并在 500 作者 / 10 VU 一格验证新增 SQL 和 P95。本次未改业务读路径。
