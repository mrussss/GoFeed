# GoFeed 模块 4 · MySQL 连接池与 Feed SQL 预算决策报告

## 现状检查

实验基准为 `9a455729d47b025840f25db21916b4c2fb23daef`，分支 `feat/feed-read-reliability`。开始时已有审计文档、Compose 配置、压缩包和 `tools/` 未跟踪，全部原样保留。实验构建从 Git 提交提取到临时目录，正式代码和提交保持现状。

- API 和 Worker 分别调用 `db.NewDB`，各自创建进程内连接池。正式初始化没有调用四项池设置，Go 的默认值为无限制 Open、Idle 2，连接最长寿命和最长空闲时间均未显式限制。实验另外检查了实际的 `sql.DB.Stats()`。
- 同一个 API 进程只创建一个业务连接池。Feed 的 Latest 时间线重建及回源、实体批量读取、Following 关系与候选检查和补齐、Popularity 排名及存在性核验、LikesCount、Tag、`BatchGetLiked` 共用 `readFeedMySQL`。本轮匿名暖 Latest 跳过 SQL。JWT 认证兜底、`/account/getProfile` 及其他业务路由、Worker SQL 在此额度之外。Following 同时经过 Feed 路由组的 SoftJWT 和保护子组的 JWT，Redis 停机时两层分别读 MySQL。认证查询错误和 Token 无效使用同一 401 响应。
- `/account/getProfile` 使用 `POST` 和 `account_id`，读取账号与四项统计。后四条 SQL 的错误在现有 Handler 被忽略，因而混合负载的成功定义同时验证 HTTP 200、账号 ID 和四个统计值。
- Feed 当前额度按单条 SQL 获取。执行上限 8，额外等待上限 8，入场等待至多 20 ms。等待或查询使用请求 Context，查询入场后从请求派生 250 ms 期限。拿到额度后以 `defer` 释放，缓存与卡片组装在额度之外。总时延可以超过 250 ms，因为同一请求可能依次进行 Redis、认证和多条 SQL。禁用预算的实验版本保持相同 SQL Context 和 250 ms 期限。在仅连接池限流方案中，等待连接也消耗该查询期限。
- API 启动后发生 Redis 故障时，Latest 回到 MySQL 分页，Following 在 Pipeline 失败时走完整 MySQL 关注查询。Pipeline 使用 50 ms 子 Context，运行时 go-redis 开启套接字阶段的 Context 期限。候选不足时的补齐查询与 Pipeline 错误后的完整回源分开计数。启动阶段 Redis 健康检查失败而禁用缓存属于另一种路径，本轮故障实验从已连接 Redis 的运行中进程注入。

## 实验口径

工具链为 Go 1.24.5、MySQL 8.0.46、Redis 7.4.11、k6 2.4.0 和 Docker 29.8.1。本机可见 32 个逻辑 CPU，实验 MySQL 的 `max_connections` 为 151。复用模块 6 的 MySQL 小档合成数据、请求模型和采集方式。连接池对照及正常负载使用同一账号（50 位关注作者）。故障请求另使用同一克隆中 64 个合成账号，每个账号 50 条关注边、三个不同的 Following 游标和一个不同的 Latest 游标，256 个请求条件覆盖 236 个不同的十视频集合。小档和大关注诊断使用新建 Schema 及独占 Redis 实例中的不同逻辑 DB。实验 Redis 开启 AOF，以便真实停机后恢复同一份种子索引。每轮新开 API 进程，预热并核对完整十条视频 ID。混合压测额外核对 Profile 的数值。按组轮换执行顺序，每组合三轮，原始记录单独保留。

连接池主实验按 20 秒执行。Following 在 10、32、64 VU 测量，Popularity 和 Latest 辅助对照在 32 VU 测量。预算正常暖负载以 10 秒执行，Redis 停机和表锁复用模块 6 的 6 秒窗口，表锁在每轮开头持有约 1.5 秒。混合业务以 64 VU Feed 加恒定 20 次/秒 Profile 请求运行 12 秒，分别测 Redis 正常和停机。大规模诊断每轮 20 秒。跨实验阶段比较只使用相同条件下的组。

主机重启中断了 Popularity 64 VU 对照。复建后的主实验二进制与原 SHA-256 一致，工具及容器版本复核一致。该组合完整重跑，初测单独保存在 `rounds-before-restart/`。其余完整组合各组三轮均来自同一运行时段，保留原有测量。

有效 RPS 按通过响应契约的完成数除以每轮设定的负载窗口，包含宽限期内完成的在途请求，成功分位数仍由通过校验的请求计算。少数 k6 汇总的运行时长与固定发压窗口不同，例如 12 秒内发出的 241 个 Profile 请求被报告为 22.65 RPS，故保留 k6 原始速率并统一重算正式表中的 RPS。全请求分位数独立记录。SQL 数量由 MySQL prepared execute 计数获取，包含认证与 Profile 时按所有 HTTP 请求计。Feed 包装执行次数另计。连接创建取 MySQL `Connections`，包括少量相同的采集连接。客户端实际执行上下文及连接池全字段、服务端进程列表样本、SQL 计时、MDL 等待、k6/API/MySQL CPU、API RSS 及累计分配保留在逐轮数据。CPU 百分比以一逻辑核为 100%。服务端峰值来自约 220 ms 采样。主要数据取三轮中位数，取峰值的字段会单独标注。表中时间单位为毫秒，RSS 和分配列使用 KiB。固定 VU 无思考时间，快速 503 会使同一 VU 更快开始下一次请求，解读时优先用成功吞吐、成功延迟和成功率。

复现材料、实验专用源码补丁和完整逐轮数据位于 [本轮实验目录](../data/feed-read-reliability/read-budget-lab-20261120T1455Z/)。

## 连接池 A / B / C

A 使用 Go 默认值，B 为 16 Open / 8 Idle，C 为 32 Open / 16 Idle，三组都保持原始 8/8/20 ms 预算和未配置的连接寿命。Following 10 VU 时，A 每轮中位数关闭 10,023 个空闲连接、新建 10,030 个 MySQL 连接。B/C 的空闲关闭中位数均为 0，新建分别为 13/12。B 对比 A，成功吞吐由 801 升至 989 RPS，成功 P95 由 18.41 降至 11.70 ms。B/C 在这一档的成功吞吐和延迟接近。

Following 32 VU 时，B/C 分别成功 425/429 RPS，503 为 85.30%/85.27%，两者均没有 Go 池等待。64 VU 时分别成功 102/103 RPS，503 为 98.46%/98.50%。C 在 64 VU 消除了 B 的少量池等待，但几乎没有改变成功吞吐。扩大池子主要解决默认空闲额度过低引发的连接周转。高并发下的成功吞吐下降伴随密集的 Feed 入场拒绝，单靠扩大池无法缓解。Popularity 32 VU 的 B/C 也分别约为 2,618/2,620 成功 RPS。

后续统一使用 B。选择规则要求 C 在至少两个 Following 并发档同时达到超过 B 的 8% 成功吞吐优势及成功 P95 无回退。本轮 C 在 10、32、64 VU 相对 B 的成功 RPS 约为 −1.2%、+1.1%、+1.2%。匿名 Latest 接近零 SQL，各池均接近满成功率。部分轮次有极少量数据库回源，逐轮计数保留。

### 正常暖缓存

Following 10 VU 下，三组都是约 1,100 成功 RPS，整页响应校验均通过。32 VU 时 S1 有 85.05% 503，S2、S3 三轮均通过校验，且成功吞吐分别达到约 1,527 和 1,233 RPS。64 VU 时 S1 成功约 103 RPS，S2 和 S3 分别约 1,629 和 1,347 RPS。S1 的 64 VU 成功 P95 为 49.60 ms，低于 S2 的 63.11 ms，但只服务了约 1.65% 的尝试。S3 的成功 P95 为 89.30 ms，共用 8 个连接的等待成本已经可见。S1 在 32 VU 没有 Go 池等待，足以将该档的早期拒绝定位到 Feed 额度。

### 真停 Redis 与 MySQL 表锁

真停 Redis 后的流量按每 VU 的多个游标交替请求。10 VU 三组约 48 成功 RPS，成功 P95 约 268 ms。64 VU 下，S1/S2/S3 约 269/304/300 成功 RPS，成功 P95 约 276/279/286 ms。S1 在途 Feed 查询峰值为 8，MySQL 采样活动峰值为 7，对应的 S2 值为 52 和 14。S2 的在途计数包含等待连接的调用。S1 仍然有观测到共享池的 16 个连接全在用，JWT 兜底等 SQL 在 Feed 限额之外。S3 把池硬限在 8 个连接，64 VU 池等待次数中位数为 1,310 次，S2 为 302 次。该故障注入中大量时间由 Redis 访问期限及认证回退占用，所以成功吞吐差距远小于暖缓存。

## 建议与待决策项

1. **API 连接池优先选 16 Open / 8 Idle。** 以 Following 10 VU 为例，默认池每 20 秒创建约一万条连接，16/8 降至 13，成功 P95 从 18.41 降至 11.70 ms。32/16 没有稳定的附加吞吐收益，8/8 在混合流量下有更严重的共享池等待。本轮未改变连接寿命和空闲连接最大存活时间。上述连接预算以单 API 进程计，API 副本数和 Worker 的独立连接池另计。
2. **保留对回源和重建 SQL 的 Semaphore，优先审查收窄 Following 的常态 SQL 范围。** 匿名 Latest 表锁下，S1 的 SQL 超时计数为 40，对比 S2 和 S3 的 128。同一限额覆盖 Following 暖路径时，32/64 VU 出现约 85%/98% 的 503。若优先保障暖路径，FallbackOnly 是本轮支持的折中候选。若 Profile 暖缓存 P95 需保持 S1 的水平，应先决策是否接受约 49 ms 的尾延迟增量。范围实验证据覆盖 Following，其他 Feed 入口仍需按各自 SQL 风险判断。
3. **收窄时以 8 个执行、8 个等待、最多 20 ms 入场等待及 250 ms 查询期限为起点。** 缩短等待或减少等待者提高了真停 Redis 时的拒绝率。把执行增至 12，在表锁下提高了超时及服务端 MDL 峰值。当前证据足够排除这些替换参数作为首选，但只覆盖所测档位与负载。
4. **把大关注列表单独看待。** 5,000 和 10,000 作者的 10 VU 请求频繁触发 50 ms Pipeline 期限并转向 MySQL。范围实验没有修改 Pipeline，也没有测分批方案。暂不能据此判断分批或调整期限的收益。

本轮保持正式代码和 HEAD 原样。没有 Commit 或 Push。主矩阵 198 轮，补充矩阵 42 轮，共 240 轮。单进程合成数据、固定并发和单一非 Feed 接口限制了外推范围。表锁用于定位过载行为，锁释放后的细粒度恢复曲线没有单独采集。所有 Profile 结果和各轮 Feed 契约错误保存在逐轮数据中。
