# GoFeed 原项目性能基线报告

日期：2026-11-16。实验目录：[`data/baseline/k6/20261116T093101Z/`](../data/baseline/k6/20261116T093101Z/)。

**结论：已实际完成 10、20、40、80、120、160 VU 六轮短时测试。2,072,606 次请求均未出现 HTTP 或脚本校验错误，五个基线容器全程无重启或 OOM。最高测试档 160 VU 的 k6 报告吞吐为 17,948.18 RPS，P95 16.752 ms、P99 22.402 ms。**

80 VU 之后出现吞吐边际收益递减和延迟继续上升的趋势。由于负载生成器与被测服务共享主机、k6 本身 CPU 开销较高，不能据此断定后端单独达到容量上限。本轮停止可选的 200、250 VU 额外摸底，不代表系统已经过载或生产环境可承载量已确定。

## 1. 安装与环境

已阅读 [k6 使用说明](../tools/k6/README.md)，通过 Grafana 官方 Ubuntu APT 仓库实际安装成功：

```text

```

原先 sudo 需要密码，使用 WSL 已提供的 root 执行入口完成已授权安装。只新增 k6 的签名 Key、APT 源和 k6 软件包；apt-get update 仅针对 k6 源刷新列表；没有系统升级或安装其他软件。安装输出为 `0 upgraded, 1 newly installed`。

## 2. 测试前检查

实际确认：

- `GET http://127.0.0.1:28080/healthz` 返回 200 和正常 JSON。

- `k6 inspect tools/k6/feed_latest.js` 成功，之后第一轮实际执行进一步确认 HTTP 访问和脚本运行正常。

## 3. 模型与执行方法

使用原有 [feed_latest.js](../tools/k6/feed_latest.js)，没有修改其请求或校验逻辑：

```text
POST http://127.0.0.1:28080/feed/listLatest
Content-Type: application/json
匿名访问
{"limit":10,"latest_time":0}
```

**固定 VU Closed Model**，executor 为 constant-vus。每个 VU 等上一请求及校验完成后立即发起下一次请求，无 sleep、无固定到达率、无性能阈值。VU 是并发虚拟用户数，RPS 是每秒请求数，两者不能混用。

每轮配置 duration=30s，gracefulStop=10s，请求 timeout=10s。六轮独立顺序执行，轮次之间至少等待 10 秒，本轮实际人工分析间隔通常更长；没有并行负载或额外预热流量。脚本检查 HTTP 200、JSON 可解析、video_list 为数组且数量不超过 10、has_more 为布尔值。

新增 [run_round.py](../tools/k6/run_round.py) 运行一轮并保存 k6 输出、容器前后状态及资源样本；[summarize_rounds.py](../tools/k6/summarize_rounds.py) 只读取保存文件生成汇总。运行器禁止使用已有同名 summary，不接触数据库或 Redis，不替代现有 k6 场景。

复现单轮示例（本轮已执行，不需要为了查看报告再次运行）：

```bash
python3 tools/k6/run_round.py --vus 10 --out data/baseline/k6/新的UTC时间戳目录
```

## 4. 各轮实测结果

延迟单位为 **毫秒**，RPS 使用 k6 的 `http_reqs.values.rate`。P50/P95/P99 取 `http_req_duration` 的 med/p(95)/p(99)，不是单次请求耗时；没有对各轮分位数再次求平均。

| VU | 配置时长 | 请求数 | RPS | P50 ms | P95 ms | P99 ms | HTTP 错误率 | 业务校验错误率 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 10 | 30s | 166,023 | 5,749.05 | 1.494 | 2.622 | 3.429 | 0.000% | 0.000% |
| 20 | 30s | 196,288 | 6,792.16 | 2.601 | 4.842 | 6.107 | 0.000% | 0.000% |
| 40 | 30s | 301,137 | 10,410.24 | 3.401 | 6.627 | 8.532 | 0.000% | 0.000% |
| 80 | 30s | 419,490 | 14,513.46 | 4.831 | 10.088 | 13.444 | 0.000% | 0.000% |
| 120 | 30s | 471,620 | 16,320.54 | 6.507 | 13.577 | 17.969 | 0.000% | 0.000% |
| 160 | 30s | 518,048 | 17,948.18 | 7.974 | 16.752 | 22.402 | 0.000% | 0.000% |

HTTP 错误率对应网络错误、超时和非 200；业务校验错误率为脚本的 `feed_request_errors`，任意 HTTP/JSON/结构检查失败即计该请求失败。检查通过不表示逐字段业务正确性已完全验证，尤其脚本允许空视频数组。

六轮 k6 均正常退出，容器 before/after 均 healthy、RestartCount=0、OOMKilled=false，资源采样无报错。

## 5. CPU 与内存采样

每轮保存 10 个资源样本。采样循环为一次 docker stats --no-stream 后等待约 1 秒，实际样本间隔约数秒；属于低频采样，可能遗漏瞬时峰值。CPU 平均为样本算术平均，最大值仅是采样峰值；内存不是堆大小或 Go GC 指标。

**百分比口径：**WSL CPU busy 以全部 32 个逻辑 CPU 为 100%；Docker 容器和 k6 进程 CPU 以一个逻辑核为 100%，因此 500% 约等于占用 5 个逻辑核。两类百分比不能直接相加或当成同一个分母。

补充观察：

- WSL 可用内存最低约 10.79 GiB；所有样本 swap 使用均为 0，没有观察到内存耗尽。
- 160 VU 时 Backend 约占 5.84 个逻辑核，k6 约占 8.67 个逻辑核，WSL CPU 平均 68.6%、采样最大 70.5%。全机尚有余量，但负载端开销已经不可忽略。
- Redis 平均 CPU 从约 39.6% 增至 74.4%（单核口径），存在随 RPS 增长的压力，尚未观察到其 CPU 持续达到单核 100%。
- MySQL 平均 CPU 约 1.4%～2.5%，未观察到 CPU 饱和。本轮主要是缓存命中的匿名首屏，不能据此代表数据库回源性能。
- RabbitMQ 采样 CPU 有明显波动，最高单次为 778.43%，但请求路径不发布业务 MQ 消息。本轮没有定位其后台 CPU 波动原因，不把它解释为 Feed 的 MQ 吞吐或故障；它是共享主机噪声来源之一。

## 6. 趋势、拐点与升压决定

吞吐从 10 VU 的 5749.05 RPS 增长到 160 VU 的 17948.18 RPS，但非线性增长；P50、P95、P99 随并发持续增加。

- 80 → 120 VU：并发增加 50%，RPS 增加 **12.45%**，P95 增加 **34.58%**。
- 120 → 160 VU：并发增加 33.33%，RPS 增加 **9.97%**，P95 增加 **23.39%**，P99 从 17.969 ms 增至 22.402 ms。

**可以确认吞吐边际收益递减，80 VU 以后更明显；不能确认一个精确的硬容量拐点。** 只有每档一次 30s 的观察，前面档位的增幅也不均匀；没有重复试验、独立压测机或明确延迟 SLO，不应把 80/120/160 VU 中任何一个直接当成系统上限。

160 VU 没有错误、重启、OOM 或明显内存瓶颈，但不满足“延迟没有明显恶化”的保守升压前提；同时 k6 自身 CPU 开销持续上升，结果已混入负载端资源竞争。因此本轮未执行可选的 200、250 VU，避免把继续升压当成必须完成的数字目标。这个决定不等于认定系统已经过载，也不等于证明更高档一定失败。

## 7. 潜在瓶颈：事实与推断

| 项目 | 本轮证据 | 能够得出的判断 |
|---|---|---|
| 压测端成本 | k6 平均 CPU 从 2.24 核增至 8.67 核，RSS 随 VU 上升 | 负载生成、JSON 解析和校验开销不低，可能与后端竞争 CPU；不能证明 k6 已完全饱和 |
| 后端处理 | Backend 平均约 2.83～5.84 核；并发增加后延迟持续上升 | 有服务端处理/调度成本，但未采集 profile，不能确定是 JSON、锁、GC 或其他函数 |
| Redis 请求 | Redis CPU 随吞吐增加；最新流每次需要读取时间线，实体缓存也可能回填 | 是后续可观察方向；未采集 Redis latency/命令耗时，不能认定已达 Redis 极限 |
| 日志及本地网络路径 | 保留 Gin 请求日志，Docker json-file，WSL 到 Docker 发布端口 | 日志 I/O、容器转发和虚拟化可能影响结果，本轮未隔离归因 |
| 数据库 | MySQL 平均 CPU 较低，时间线与实体缓存自然保持热度 | 暂无 MySQL CPU 瓶颈证据；未统计每请求 SQL 次数，不能扩展成数据库无瓶颈结论 |

要区分后端与 k6 瓶颈，后续优先在相同场景下用独立负载机或限制干扰源复测，并结合服务端 profile；本轮没有擅自变更资源配额、日志级别、业务代码或 Compose 来优化成绩。

## 9. 实验限制与结论

1. 单台 WSL2/Docker Desktop 主机同时运行负载端、被测服务和其他旧项目容器，非独占服务器；不能外推生产环境承载能力。
2. 每档只运行一次、配置 30s，没有长稳、重复分布、置信区间、冷缓存对照或多机实验。
3. k6 原始统计时间窗与 30s 配置存在未解释差异，复测前需要复核；本轮保留所有原始值。
4. 只测试匿名最新流固定首页、limit=10，不覆盖登录点赞查询、关注流、分页、冷尾 SQL、热榜或混合读写。
5. 缓存没有清理或人为预热，但自然 TTL 和进程缓存状态随轮次变化；各轮缓存状态不保证完全一致。
6. 本轮脚本只检查列表数量不超过 10，不对每条视频或完整业务排序逐项断言；零业务校验错误不等于所有业务逻辑均已验证。
7. 未采集每请求 SQL 次数、Go profile/GC、磁盘 I/O 或 Windows 宿主机的完整压力指标；资源峰值只指采样峰值。
8. 未设置性能达标阈值，不能把“零错误”写成满足某个未定义 SLA。

**本轮获得了可追溯的原项目匿名最新流短时测量结果，可作为后续同环境、同场景对照的初始参考。最高已测档为 160 VU，未测得故障上限；后续二开比较应保留同一脚本、数据集和统计口径，并复核时间窗与共享主机干扰。**
