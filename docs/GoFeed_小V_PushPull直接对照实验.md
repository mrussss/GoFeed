# GoFeed 小 V · Pure Push / Pure Pull 直接对照

**Pure Push 稳定降低了 K=100 的候选读取成本，但没有稳定降低完整 Service 延迟。** 500 粉丝下，Push 每 120 条发布多执行 119,760 条 Redis 写命令。在本次图谱和读量下，证据不足以证明读取收益可以摊平写扩散，也不足以支持新增 `has_pull_history`。

## 基准与实验设计

基准为 `main` 的 `71f9713b394c90ed1d0b0d2334566860cd6207bf`。本地 `HEAD`、`origin/main` 和 GitHub 返回的 `refs/heads/main` 一致。隔离脚本从该 SHA 导出临时源码。在发布事务内由测试上下文指定快照模式，在 Following 读取中由测试上下文选择 Inbox 或作者 Outbox，外加整页回源计数。仓库中的发布策略、9,000/10,000/11,000 阈值、业务读路径和已有实验文件均未改动。

| 控制项 | 设置 |
| --- | --- |
| 环境 | 独立回环 MySQL 8.0.46、Redis 7.4.11（DB 15，AOF 关闭，沿用默认 RDB）、Go 1.24.5、Docker Desktop 29.8.1、WSL2 Linux 6.18.33.2，i9-14900HX，32 个逻辑 CPU |
| 图谱 | 每档 K 位作者，每位恰好 500 粉丝。100 位粉丝共享关注全部作者（含测试读者），另有各作者 400 位独有粉丝。每格独立 MySQL Schema、Redis 前缀和 Go 测试进程 |
| 视频 | 每格 120 条，总数固定。种子 `20261123` 固定作者分配、ID、发布时间及发布顺序。K=2 每作者 60 条；K=100 每作者 1–2 条。使用同毫秒的多条视频覆盖复合游标 |
| 写入 | 两组通过正式 MySQL `Publish` 事务，分别固化 Push/Pull。统一读取数据库 Outbox 快照，调用正式 `timelineEvent` 和 `writeFollowingCandidates`。120 个事件均完成后才读取。直接调用跳过轮询、MQ 传输/Confirm、发布标记、ACK、全局时间线与 MQ 重投。实测分发时间是候选函数，从进入到返回，包含粉丝分页、写入与裁剪 |
| 读取 | Pure Push 只查 Inbox，Pure Pull 查全部 K 个作者 Outbox。保留正式的关注列表 SQL、堆归并、去重、候选核验、实体 L1/Redis/MySQL 批量装配、Singleflight、点赞查询和分页。相同 16/8 API MySQL 池、回源预算、50 ms Redis 子期限 |
| 正确性 | Fanout 后逐键核对键数、候选 Member、Score、总量；Redis 保留上限 Inbox 1,000 / Outbox 500。用独立 SQL 给出视频 ID、时间倒序与点赞状态。跟随真实响应的游标遍历 12 页及空尾页。再预热 30 次，最后按同一固定页序列读取 200 次，核验每次的 ID、顺序、点赞状态、游标与 `has_more` |
| 轮次 | 同一 K 内第 1 对 Push→Pull、第 2 对 Pull→Push，串行执行。尝试在夹具与预热开始前登记，运行器不自动重试 |

相同 K 内两组的数据与操作一致。跨 K 时，关注关系总量、发布分散度、每位独有粉丝的索引形状也随 K 改变，所以跨 K 的绝对数字不能当作只改变 K 的生产系统对照。 [源码及复现步骤](perf-evidence/small-v-direct/README.md)

**实际执行 8 次尝试，8 轮有效，每配置 2 轮，无重试及失败。** 8 轮共正式读取 1,600 次，响应错误、分页契约错误、Pipeline 超时和整页 MySQL 回源均为 0。所有样本纳入汇总。K=100 两个配对的 Service 延迟方向不同，保留原值，不补跑。 [尝试台账](perf-evidence/small-v-direct/measured/attempts.csv) · [逐轮日志、环境与构建记录](perf-evidence/small-v-direct/measured/)

本轮使用的 Redis 在实验结束时累计记录 4 次 RDB 保存，无正在执行的保存，实验 DB 15 已清空。未采集每次 RDB 保存与请求的时间对应，无法将轮间时延波动归因于 Redis 持久化。

## 写入成本

时间列为两轮对应统计值的中位数。写命令、键数和键级内存两轮一致。Redis 内存按索引键累加 `MEMORY USAGE`，在读取预热前采样，不含实体缓存或 Redis 进程开销。

| K | 策略 | ZADD / 裁剪命令 | 索引键 / 成员 | 索引字节 | 发布事务 P50 ms | Fanout P50 / P95 ms | 120 条 Fanout 累计 ms | Fanout MySQL SELECT |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | Push | 60,000 / 60,000 | 900 / 60,000 | 2,646,400 | 28.99 | 9.15 / 11.22 | 1,115.43 | 240 |
| 2 | Pull | 120 / 120 | 2 / 120 | 5,328 | 25.58 | 1.21 / 1.88 | 147.74 | 0 |
| 100 | Push | 60,000 / 60,000 | 40,100 / 60,000 | 6,665,600 | 31.90 | 9.67 / 14.45 | 1,222.86 | 240 |
| 100 | Pull | 120 / 120 | 100 / 120 | 16,160 | 30.51 | 0.61 / 0.82 | 74.09 | 0 |

- 每组均完成 120 次发布与分发，无 Fanout 函数错误或应用层重试。Push 每条视频向 500 个 Inbox 写并裁剪，按批读一次 500 行，再查一次空页确认结束。Pull 只写和裁剪一个 Outbox，省去粉丝查询。**Push 每批多 119,760 条 Redis 命令、240 次 Fanout SELECT**，索引多 2,641,072 B（K=2）或 6,649,440 B（K=100）。120 条候选分发累计时间约多 0.97 秒或 1.15 秒。
- 每个策略的发布事务为 360 次 SELECT、120 次 COMMIT。K=2 有 242 次 INSERT，K=100 有 340 次 INSERT，包含作者状态首建、视频与快照。在两个策略之间，发布语句数量一致。读取待发快照的额外 1 次 SELECT 单独计数，未纳入两段时延。发布时间差异不能推断为模式本身加速事务。
- Fanout 的两轮累计范围（Push 对 Pull）为 K=2 的 1,040.00–1,190.86 ms 对 139.71–155.78 ms，以及 K=100 的 1,044.83–1,400.89 ms 对 68.56–79.61 ms。批次累计是 120 次串行调用时长之和。MQ 排队后的可见耗时和生产吞吐未测。 [写入逐轮](perf-evidence/small-v-direct/measured/write-rounds.csv) · [逐视频时间](perf-evidence/small-v-direct/measured/)

## 读取性能

每行是两轮的中位数。括号为两轮的 Service P95 范围。Pipeline 通过 go-redis Hook 计时，从执行到返回，含传输与解码，命令对象和 Key 的构造在 Hook 之前。Service 时间含正式候选、核验和组装。成功速率分母是整个闭环窗口，包含测试侧断言开销。这里没有 HTTP、JWT 与网络请求入口。

| K | 策略 | Service P50 / P95 ms（P95 范围） | 候选命令/请求 | Pipeline 平均 / P95 ms | 成功请求/s | 实际 SELECT/请求 | SQL Trace ms/请求 | 分配 KiB/请求 | Go CPU % / µs 每请求 |
| ---: | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | Push | 5.64 / 7.00（6.67–7.33） | 1 | 0.74 / 1.00 | 174.95 | 3 | 4.86 | 38.85 | 26.85 / 1,535 |
| 2 | Pull | 6.55 / 13.78（13.03–14.53） | 2 | 1.09 / 1.98 | 120.36 | 3 | 7.05 | 40.21 | 27.20 / 2,261 |
| 100 | Push | 6.95 / 10.36（8.01–12.71） | 1 | 0.94 / 1.32 | 138.05 | 3 | 6.30 | 45.71 | 27.79 / 2,081 |
| 100 | Pull | 6.72 / 8.46（8.12–8.79） | 100 | 1.36 / 1.76 | 146.08 | 3 | 5.27 | 110.30 | 30.00 / 2,052 |

SQL 以 MySQL 的 `Com_select` 增量计算，每轮 600 条，GORM 实际 Trace 也为 600 次。三条为关注作者、候选核验和点赞状态。Trace 是 Go 看到的语句时长，含构造、池与网络等待、服务端执行和扫描，不能当成数据库 CPU。约占 Service 平均时长的 77%–85%，是本实验最大的固定路径成本。Go CPU 取进程 CPU 时间差，100% 等于一个逻辑核。分配取累计分配差值，均包含测试埋点。每项计时保留所有请求，未排除结果异常或回源请求。此次超时率、整页回源率与错误率均为 0。 [读取逐轮](perf-evidence/small-v-direct/measured/read-rounds.csv)

- **K=2。** Push 在两个配对中 P50 和 P95 均更低，Pipeline 平均节省约 0.35 ms，分配只省约 1.36 KiB。Service 平均差约 2.59 ms，但其中约 2.19 ms 同时出现在完全相同的 SQL 路径上。两轮观察到 Service 优势，稳定可归因的是候选命令与 Pipeline 的降本，不能把整段 Service 差值全归给 Inbox。
- **K=100。** Push 把候选命令从 100 降到 1，Pipeline 平均约降 31%，分配约降 59%，两个配对的方向一致。Service P95 配对一为 Pull 8.79 → Push 8.01 ms，配对二为 Pull 8.12 → Push 12.71 ms。CPU/请求也在两对间反向，整体中位数略高。SQL 路径仍占多数时间，读候选变轻并未兑现为稳定的 Service 延迟或吞吐提升。

## 读写能否摊平

以固定 **120 条发布**为单位，设 `R` 是在这些索引仍有效时、与被测共同粉丝同样读法的请求数。某资源的条件分界为 `额外写成本 / 每请求读节省`。只有分母为正且读写属于同一量纲时该分界才有意义。表内用两个配对差值的中位数作比例，括号为各配对分别计算的范围。

| 独立成本口径 | K=2 | K=100 | 假设与适用范围 |
| --- | --- | --- | --- |
| Redis 命令字面计数 | 119,760 读请求 | 1,210 读请求 | 119,760 条额外写命令，读侧分别每次少 1 或 99 条。命令等权只用于判断调用数，不代表时间或可用容量。 |
| Redis 服务端命令执行微秒 | 约 15,150（13,171–17,567）读请求 | 约 924（785–1,076）读请求 | 额外写执行约 222 / 193 ms，每次读执行节省约 14.65 / 209.45 µs。只衡量 ZADD、裁剪和候选 Lex 命令，未计网络、内存、MySQL 或持久化。 |
| Go 进程 CPU 时间 | 约 579（459–753）读请求 | 无稳定分界 | 只用 Fanout 的额外 Go CPU 与读取 Go CPU/请求差。K=100 一个配对省约 379 µs，另一个多约 437 µs。 |
| 串行等价的调用墙钟 | 约 373（318–437）读请求 | 无稳定分界 | 额外 Fanout 函数时长除以读均值差，假定同样的等待时间可相加。K=2 的分母尤其受同路径 SQL 时延波动影响。K=100 一个配对省 0.73 ms，另一对反而多 1.81 ms。这不是端到端容量模型。 |

内存与额外 MySQL 访问不能用以上比例相消。Push 多出的 **2.52 MiB / 6.34 MiB** 候选内存在索引保留期内仍需付出，读取本身不会使它减少。每批多出的 240 次 MySQL SELECT 在暖读取中也没有对应的语句数节省。只有 100 位共同粉丝具备被测的 K，400 位独有粉丝只关注其对应作者。不能把一次高 K 读取的节省乘到每位粉丝上。正式测量的 200 次读取规模低于两个档位上述 Redis 命令计数与服务端时间分界。

缺少各类读者的 K 分布、活跃读频与发布率的联合观测，还未覆盖并发发布与 MQ 积压、索引存活与内存预算、可见性 SLA。因此可以给出分资源的数量级，尚不足以得到可信的生产盈亏平衡点。尤其不能将候选命令减少 99% 解释为 Service 延迟减少 99%。

## 结论

1. **Q1 · 读取优势。** K=2 的两个配对确实观察到 Push 的 Service P50/P95 更低，但较大的整体时延差伴随 SQL 耗时波动，能稳定归因的候选成本差较小。K=100 的 Inbox 物化已经显著降低候选命令、Pipeline 和 Go 分配，未表现为两轮稳定的 Service 延迟或吞吐优势。
2. **Q2 · 500 粉丝的额外写扩散。** 当前证据不足以证明可抵消。K=100 的 Redis 服务端开销模型提示每 120 条发布需约千次同形读取，K=2 需约万次。该结论只适用于相同测量窗口与 Redis 命令执行时间。写入、内存、额外 MySQL 和生产业务分布都限制外推。当前图谱和读量下，如果优先优化写扩散、索引空间和复杂度，Pure Pull 更经济。
3. **Q3 · 生产是否需要 `has_pull_history`。** 暂无充分依据。纯 Push 的只读 Inbox 是理想结果，生产混合读者仍要读当前 Pull 与历史 Pull 作者的 Outbox。历史判定还会增加读取或迁移成本，且需正确处理跨阈值、重放与旧数据。当前隔离环境连 K=100 的完整 Service 收益都未稳定，不能据此引入生产元数据。 [历史行为与安全边界](GoFeed_Hybrid_Push读取收益诊断报告.md)

此前 K=1–2 的对照中，Pull 的多作者读取代价很小，正式 Hybrid 即使 Push 也会发所有 Outbox 请求，难以摊销粉丝级写入。本次用真正的 InboxOnly 取得了可归因的候选读取优势，证明“小 V Push、大 V Pull”有工程上的成本取舍。**大 V Pull 的写扩散收益有直接证据，小 V Push 的总体收益仍取决于读者是否频繁阅读较大的关注列表。** 双阈值是控制写放大与抑制切换的工程配置，实验未搜索或证明其最优。 [此前综合验收](GoFeed_三亮点最终简历证据验收.md)
