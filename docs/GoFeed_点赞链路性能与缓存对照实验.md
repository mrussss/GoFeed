# GoFeed 点赞链路性能与缓存对照实验

## 1. 执行摘要

完成并通过对账的正式轮次包括 HTTP 基线 30 轮、Worker SQL×分区 36 轮、缓存筛选 12 轮、缓存复测 18 轮、最终 HTTP 对照 6 轮。另有早期探测及失败重试日志保留。

推荐提交人工评审的组合为 **批量 SQL + 按视频分区 + 统一 Video Key**。在 800 命令/秒的单热点 Worker 对照中，每次 ACK 的显式 SQL 从 2.053 降至 0.089，事务 P95 的轮次中位数从 93.36ms 降至 28.73ms。统一 Key 的正式复测显示回源与原版基本相当，小幅节约对象存储。1 秒拆分可显著降低热点回源，但分散读取代价较高，暂不推荐通用启用。

完整链路的主要限制仍在 **A2 单 Relay**。50 请求/秒写入场景里，原始版和推荐版的 Relay 活跃发布约为 29–30 条/秒，队列积压主要出现在 Outbox。该窗口内 MySQL 标记平均比 Confirm 更耗时，优先分解两段成本。最终实验版本保存在隔离源码与数据归档中，业务源码维持在本报告所列 Commit。

## 2. 代码与环境基线

实验基于 `feat/like-reliable-ingress` 的 `484b7a4`。HTTP 在 MySQL 提交意图和关系 Revision 后返回 202。单实例 A2 Relay 逐条等待 Publisher Confirm 后写 `published_at`。四个持久化分区各有一个消费者。Worker 批上限 50、等待上限 20ms，事务提交后执行缓存失效，再发送 ACK。

实验使用独立 Compose 项目 `gofeed-perf`，每个服务配额 2 CPU / 2 GiB。WSL2 宿主为 i9-14900HX、32 个可见逻辑 CPU、约 15.5 GiB 内存。MySQL 8.0.46、RabbitMQ 3.13.7、Redis 7、k6 2.4.0；实验二进制由 Go 1.24.5 构建。每组环境文件记录了镜像 ID、源码与二进制哈希、统计版本和资源配置。压测机和服务共享主机。

数据集固定种子 20261116，包含 1000 用户、10000 视频、100000 点赞和 20000 关注。每轮恢复前校验 CSV，归档数据、负载、源码和运行参数。缓存混合负载把热点视频设为最新以让 Feed 命中该视频。旧匿名 Feed 测试的路径与用途见 [旧基线报告](GoFeed原项目性能基线报告.md)。

## 4. 批量 SQL 对照实验

S1/S3 用排序后的 tuple IN 对复合索引查行加锁，再用 CASE 更新关系。关系 Revision 校验、视频计数增量和 Outbox 语义保持一致。Worker 三档分别输入 100、400、800 命令每秒，前 15 秒预热，后 60 秒统计。输入通过 A1 持久化并分配 Revision，测试发布器验证载荷后将其直接送入四分区。各场景的 12 轮归一化意图 SHA 一致。

使用 pair 路由时，批量 SQL 在均匀、幂律和单热点下每次 ACK 的显式 SQL 分别减少 **24.1%、62.3%、91.8%**。幂律下 pair 路由的事务 P95 几乎不变，行锁等待仍高。按视频路由后，批量 SQL 进一步缓解了单热点队列积压。四种组合在测得档位的 ACK 速率接近输入，因此当前证据支持 SQL 降本与事务延迟收益，容量上限仍未测定。

## 7. 视频缓存实验

1/3/5 秒 TTL 的热点短筛选估计陈旧 P95 上界按详情约为 0.93/2.78/4.68 秒。正式 1 秒复测也记录了超过 1 秒的上界，包含并发回填、SQL 观测间隔与可能跳过的计数历史。不能据 TTL 对响应陈旧性作硬保证。3 秒立即失效在筛选中仍有 244 次 DEL 和 254 次热点回源，收益不如 TTL 方案。建议保留 1 秒结果作为高热点专用改法的证据，当前通用负载采用统一 Key。

50 请求/秒的两类写入场景均复现 Outbox 增长。热点写入在原始版与候选版的 Outbox 峰值分别为 690/700，MQ ready 的管理采样峰值均为 0，测量期 ACK 约 25.9/25.5 条每秒。A1 能持续受理，Worker 隔离档位显著高于端到端发布速度，因此本环境的首要限制在出队发布阶段。RabbitMQ 管理采样可能漏掉短时尖峰，最终以直接 broker 队列查询核验。

## 9. 正确性验收

复核 HTTP Request ID 幂等、Revision 正确性、事务提交和回滚、RabbitMQ 断链重连与 ACK、Redis 故障下点赞提交及读取回源。各组正确性门禁保存 `correctness-*/tests.log` 和源码归档。缓存门禁验证 L1/L2、TTL 到期、序列化契约和延迟回填竞态。关注流客户端状态仍以关系 Revision 和最终 MySQL 状态验收。

测量后联合验证 Outbox pending、关系 Revision 和 broker ready/unacked 归零，再逐视频核对有效关系和计数。离线校验按每组数据集、初始关系和最终事件重建预期状态。早期基线中部分轮次仅有在线对账，后续候选均保存逐行快照供独立复核。详细日志保留在各相应实验目录。

候选组合第一次正确性检查在系统墙钟回退时触发排序断言，之后用相同源码原样重测通过。两轮日志分别保存在 [首次失败](../data/perf/correctness-CacheB-S3-20261118T024306832841Z/tests.log) 与 [通过的重测](../data/perf/correctness-CacheB-S3-20261118T024407201763Z/tests.log)。依赖墙钟更新时间的列表存在时钟回退风险，建议评审时确认为已知限制。

## 10. 最终建议

1. 保留批量 SQL，先以候选方式审核索引、事务 SQL 和回滚路径。单热点与视频路由组合收益最大，均匀负载下也降低了显式 SQL 开销。
2. 热点写入优先按视频分区并配套批量 SQL。分区改动应在发布和消费两端同步，并有切换前排空和回退方案。评审时需要考虑单视频聚集分区及更高输入时的余量。
3. 统一视频 Key 值得进入人工评审，主要收益来自删除重复存储与简化失效契约。按三轮正式结果描述尾延迟和回源的变化幅度。
4. 通用路径保留完整视频对象。对单热点专用拆分方案可优先研究 1 秒 TTL，启用前应定义陈旧性目标和分散读取的 MySQL 预算。暂不推荐 3/5 秒默认 TTL 或每次立即失效的拆分。
5. A2 单 Relay 是优先优化方向。必须先区分发布 Confirm 和 MySQL 标记的耗时，后续再考虑发布架构改动。
6. 简历可引用明确档位和对照的 SQL/ACK、事务 P95 和行锁等待指标，注明本机隔离 Worker 场景和三轮中位数。不能用 HTTP 202、既定输入档位、单机结果或短筛选推导生产环境最大吞吐。

## 11. 实验限制

共享 WSL2 资源使尾延迟存在轮间波动。固定到达率用于对照既定负载。缓存陈旧区间是依靠 SQL 采样历史识别的估计区间，TTL 是缓存存活配置，二者测量口径不同。重复计数值或出现于样本缺口的历史只能标记为未知。探针额外产生约 10 次 HTTP 读取和最多约 100 次 SQL 采样每秒，真实比例和误差见逐轮 freshness 文件。重点读取负载用了最新 Feed，关注流整页缓存的时效性应另行测定。Redis Key 字节来自采样时的 `MEMORY USAGE`，总 Redis 内存另由 `INFO memory` 保留。

MySQL 8.0 digest 快照未覆盖本实验中 GORM 的大量 Prepared Statement，回源使用实验 GORM 回调计数并保留全局 SQL 和 Worker 显式 SQL 指标。该边界见 [MySQL 缺陷 #114480](https://bugs.mysql.com/bug.php?id=114480)。RabbitMQ 管理统计可能延迟，排空以直接 broker 查询和数据库联合验收为准。缓存首次门禁重试、服务器重启、慢观察 SQL 及处置详见 [执行日志](../data/perf/experiment-chronology.md)。
