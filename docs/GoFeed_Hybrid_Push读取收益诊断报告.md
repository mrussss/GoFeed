# GoFeed Hybrid 分发 · Push 读取收益诊断

**推荐 A，保留当前 Hybrid，不继续二开。** 当前读路径确实对始终 Push 的作者发送空 Outbox 查询。跳过后，K=500 的 Pipeline 平均延迟从 **1.341 降到 0.509 ms**，Go 分配从 **366.54 降到 72.28 KiB/请求**。Service P95 从 7.52 降到 6.19 ms，幅度约 18%。K=2 的 Service 中位延迟只低约 0.03 ms，K=50 未观察到稳定时延改善。确认了较大关注表的可优化开销，但缺少目标用户的读写分布，以及生产历史识别的成本证据。

上次 Pure Pull 更经济的主因是，两位作者的实验图谱使按作者读取很便宜，而 Push 每条视频先为 1,000 或 12,000 名粉丝写候选。当前代码又保留了所有 Outbox 查询，抵消了期待中的 Push 读侧命令节省。前两者是负载规模和 Push 固有的成本结构，后者是实现取舍。

## 一、源码诊断

执行时 `main` 为 `e9f1e4f82654951100250f617ac7b290bc92738f`，与本地 `origin/main` 引用一致。诊断临时源码从该提交导出。业务代码、候选策略及 9,000/10,000/11,000 阈值保持原样。

| 问题 | 实际代码与结论 |
| --- | --- |
| A · 始终 Push 的作者是否被查 Outbox | 是。登录读者在 Redis 可用时先用 MySQL 查全部关注作者的 ID；无关系时直接返回。随后构造一个 Inbox 加每位作者一个 Outbox Key，不读作者模式。正常候选 Pipeline 的命令数为 **K+1**，空键也会实际发送并返回空数组。Redis 未配置或 Pipeline 失败时走完整 MySQL 查询。 [Following 入口与 Key 构造](../backend/internal/feed/following.go#L19) · [关注关系查询](../backend/internal/social/repo.go#L72) |
| B · Pipeline 的分段成本 | Go 先构造 Key、命令参数、命令对象与结果切片。Pipeline 仍需逐条编码 RESP、写入套接字、由 Redis 执行并逐条接收解码。Hook 可观测执行入口至返回，涵盖连接等待、传输、Redis 执行及解码，计时不包含此前的命令对象构造，也不包含之后的结果切片整理和归并。可用应用计时、Hook、Go pprof 和 Redis `INFO` 分别定位，单个 Hook 无法独立分摊网络与解码。 [批量 Lex 实现](../backend/internal/middleware/redis/zset.go#L103) |
| C · Push 实际省了什么 | 候选已经在一个 Inbox 排好。同一图谱下 Outbox 为空时，非空来源较少，能少传已物化候选并降低堆的推进和去重工作。当前仍构造并发送 K+1 条候选命令、扫描所有来源。随后最大堆按时间和 ID 取 `limit+1`，MySQL 核验候选存在、关系和时间。实体走 L1、Redis 批读以及缺失时的 Singleflight/MySQL 批读，登录态再查点赞状态。暖满页实有 3 条 SELECT。候选不足时还要做整页 SQL 补齐。 [归并与校验](../backend/internal/feed/following.go#L53) · [实体回填](../backend/internal/feed/service.go#L45) · [卡片与点赞](../backend/internal/feed/service.go#L456) |
| D · 为什么不能看当前模式跳过 Outbox | 当前状态表只记录模式。视频和发布 Outbox 在同一个事务内固化当时的策略，Worker 按事件快照分发。作者 Pull → Push 后，旧视频仍在作者 Outbox，新视频写入 Inbox，旧 Pull 消息还可能重投。若只读当前 Pull 作者，可能跨过一个旧视频的排序位置。 [状态与阈值](../backend/internal/video/author_feed.go#L29) · [发布快照](../backend/internal/video/video_service.go#L41) · [Fanout 快照消费](../backend/internal/worker/following_fanout.go#L78) |

实验仍保留 API 16 Open/8 Idle、回源查询独立预算与正常 SQL 超时。50 ms Redis 子期限从 Key 构造之后开始，包含 Redis 命令构造和执行。长期 Push 省下的是非空候选流的读取和归并，并没有避免空查询开销。

## 二、Pure Push 两路径对照

### 方法与执行记录

使用上次实验的专用 MySQL 8.0.46、Redis 7.4.11 容器，Go 1.24.5，WSL2 6.18.33.2。宿主环境可见 i9-14900HX 的 32 个逻辑 CPU。各轮使用独立测试进程及 Redis 前缀，串行运行。

- **Current** 通过正式 Service 读 Inbox 加所有作者 Outbox。**InboxOnly-Diagnostic** 在临时构建中由测试上下文提供空的 Outbox 读取集合。两组都查 MySQL 关注关系，仍执行同样的候选核验、实体装配、点赞查询、Singleflight 和分页逻辑。
- 固定种子 `20261122`。每个 K 下同一读者关注 2、50 或 500 位作者；各档均 600 条视频，所有作者和视频快照均为 Push。用夹具直接构建 Fanout 已完成后的 Inbox，所有候选在 1,000 条保留限制内。逐项将 Inbox 排序和 MySQL 对照，并检查每位作者的 Outbox Key 都不存在。数据绝对完整只用于本实验，既有的缺项分页漏洞仍然存在。
- 每轮预热 30 次，轮询前三页、每页 10 条。正式测量约 4 秒，一个闭环请求流，轮询同样页面。所有返回逐次核对 ID、排序、游标和 `has_more`。独立 MySQL 基准在计时前生成，校验不计在 Service P50/P95 的调用时间内。成功请求/s 按完整闭环窗口，包括客户端断言时间，口径是本地 Go Service，未测 HTTP、JWT 或生产吞吐。
- 同一 K 内先 A→B，再 B→A。6 格各 **2 次尝试，12 次计时，12 次有效，0 次重试，0 次失败**。共 11,663 次请求，零响应错误，零 Pipeline 超时。预热、跨模式功能门禁和 SQL 核验不计为性能轮次。 [尝试台账](perf-evidence/hybrid-push-diagnostic/measured/attempts.csv) · [全部原始结果](perf-evidence/hybrid-push-diagnostic/measured/rounds.csv)

均为对应两轮的中位数。Redis 入站/出站字节是专用实验实例 `INFO stats` 差值，包含少量监控命令开销。服务端时间是 `cmdstat_zrevrangebylex.usec` 增量除以请求数。

| 2 | 2.5 → 1.6 | 3.1 → 1.8 | 12.7 → 10.9 | 482 → 155 | 467 → 459 |

- K=500 的 Current 中，Key 和命令构造已花约 221 µs/请求。两轮增量分配 profile 显示 `zRevRangeBy` 累计约占采样分配量的 50%–52%，`NewStringSliceCmd` 自身占 12%–13%，`Client.Key` 累计约占 17%。这些有调用树重叠，不能相加。命令对象、参数、Key 和批量切片是证据最明确的 Go 分配成本。 [第一轮分配](perf-evidence/hybrid-push-diagnostic/profiles/k500-current-r1.alloc-after.txt) · [第二轮分配](perf-evidence/hybrid-push-diagnostic/profiles/k500-current-r2.alloc-after.txt)
- 同规模的 CPU profile 可见 RESP 写入、读取和系统调用；更少的 Key 明显降低了请求字节。空响应很短，节约的响应字节少于请求字节。Redis 服务端执行下降约 110 µs，量级远小于 Hook 测到的约 831 µs 差异，因此仅凭 Redis 执行时间无法解释全部差异。Hook 内的 TCP/缓冲写入、等待和解码无法用现有观测精确拆份，也不能用两个跨层时长相减后，把差额全部归给网络。 [两轮 CPU 样本](perf-evidence/hybrid-push-diagnostic/profiles/)
- 暖路径的三次 MySQL 查询和卡片组装在两组均存在。K=500 即使只有一条候选命令，分配仍高于 K=2 的 InboxOnly，因为还要读出并处理较长的关注列表。候选命令降幅不能换算为相同比例的 Service 延迟或 HTTP 延迟。

## 三、Hybrid 跨阈值历史读取

同一用户关注三位作者。A 只有 Push，B 当前 Push 但有一条历史 Pull 和一条新 Push，C 当前 Pull。相同毫秒内有多个视频，C 的一条视频同时留在两个索引模拟重复候选。通过夹具声明 B、C 需要读 Outbox。同一套查库与排序校验用响应发出的游标翻页，并与独立 MySQL 顺序、ID、`has_more` 比对。功能测试未压测。

| 检查 | Current | 历史集合选择 | 结论 |
| --- | --- | --- | --- |
| 两页各三条及空尾页 | `490026, 490025, 490024, 490022, 490021, 490020`，共 12 条候选命令 | 相同 ID、顺序和游标，共 9 条候选命令 | B 的旧 Pull 视频 `490022` 保留，C 的重复视频只出现一次，同毫秒按 ID 倒序 |
| 删除 B 的旧视频、取关 C，Redis 保留原成员 | `490026, 490025, 490020`，共 6 条命令 | 相同结果，共 4 条候选命令 | 删除和取关成员未出现在结果中 |
| 仅按当前模式保留 C 的 Outbox，第一页 4 条 | MySQL 基准第 4 条是 `490022` | 错误分支第 4 条变为 `490021` | 变体人为制造缺项，剩余候选凑满 `limit+1`，现有补齐不会触发 |

[功能原始日志](perf-evidence/hybrid-push-diagnostic/measured/history.log)包含负向对照。现有生产分页缺陷发生在真实索引缺项的情况下，错误跳过 B 会独立制造同类缺项。正常的选择性读取在完整夹具通过，只说明历史集合正确时可以省掉空查询。

### 生产可行性

| 方案 | 正确性与开销 |
| --- | --- |
| 只读 `author_feed_states.distribution_mode` | 当前字段不记录历史。B 的负向对照证明不可采用。 |
| 用现有视频或发布 Outbox 快照查询历史 | 两处都记录发布时模式，可用于回填或审计。现有表没有已验证的低成本、覆盖完整历史的模式读取索引。逐次按作者查历史会增加 SQL，删除、旧数据、重放中的延迟事件也需要区分。 |
| 发布事务保存单调的“可能有 Pull 历史”标记 | 最小安全候选是只给有完整历史的新作者确立“已知从未 Pull”，首次 Pull 在视频/Outbox 事务内写入“可能有 Pull”，之后不因切回 Push、删视频或 Redis 裁剪清除。缺行、迁移不确定或读失败的作者继续查。可尝试在原关注列表 SQL 做一次 JOIN，增加的是扫描和索引访问，即使 SQL 次数不变也要实测。 |
| 以 Redis 记录 Key 不存在 | 单独查 `EXISTS` 仍需为 K 个 Key 构造和发送命令，并引入额外阶段。Redis 重启/驱逐、延迟事件重投以及并发发布会让负缓存过期。丢失或不确定时必须视为“可能存在”。当前没有证据表明这种检查比原 Pipeline 更便宜。 |

如果以后确需推进，优先验证上述单调持久化标记和同一关注查询 JOIN。首次 Pull 要先提交标记，再允许 MQ 分发，读取需要从具备所需一致性的 MySQL 路径取标记。若请求在标记提交前读到“从未 Pull”，同一请求随后仍可能跨过新入索引的视频。上线前要约定读一致性的时间边界并复测这一并发窗口。Redis 丢失时标记仍有效，但无法恢复本来就缺失的候选。重复事件保持“可能有 Pull”，删除与裁剪保留保守的额外读取。必要测试是旧数据默认未知、跨模式并发和重投、Redis 清空恢复、删除/取关及新增 JOIN 的代价。当前保留既有路径，未实现标记、迁移或生产优化。

## 四、为什么上次 Pure Pull 更经济

对作者 `a`，令 `p_a` 为发布率，`F_a` 为粉丝数，`R_a` 为生产窗口内包含该作者的读者请求数，`K` 为具体读者的关注数。粉丝数不是读次数，沉默粉丝仍承担 Push 写入。

| 成本 | Push | Pull 或共享成本 |
| --- | --- | --- |
| 候选写入 | 约 `2 × p_a × F_a` 条 Redis 命令，另有粉丝分页、批次和异步分发。 | 一条视频写并裁剪一个作者 Outbox，约 `2 × p_a` 条。Hybrid 按作者加总。 |
| 候选读取 | 正式路径仍有 `K+1` 条。Push 提前物化候选，使 Outbox 非空来源较少。 | 正式路径同样是 `K+1` 条，非空作者越多，返回和归并成本越高。安全跳过空 Outbox 后，读命令为 Inbox 加实际需查的 Outbox，每个跳过的作者每请求最多省一条。 |
| Redis 索引内存 | 每位粉丝持有自己的 Inbox，候选被复制至多个键，并受每键保留限制。 | 作者候选由读者共享，空间取决于活跃作者及保留量。 |
| SQL 和卡片 | 关注关系、候选核验、点赞，以及可能的实体缺失或整页回源。 | 相同的基本路线。候选形状、缓存冷热和回源会改变实际成本。 |

上次“8 发布/96 读取”把操作类型加权为读多，但每个读者只关注 **1–2 个作者**。Pure Pull 只需要很少的非空归并来源。Current 的 Pure Push、Pure Pull 与 Hybrid 都对同一批请求发送 Inbox 和全部 Outbox 查询，读 SQL 都约为 348/96，即 3.63 条/请求。更多关注作者也不会自动减少这几条 SQL。Pure Pull 在该轮型仅 16 条候选写，Hybrid 8,008 条，Pure Push 104,000 条。即使为这 96 个读请求安全跳过每人最多两个 Outbox，最多节省 192 条读命令。两类命令的执行成本不同，命令数上界只能说明为何这次负载难以回收额外的写扩散，不能换算成同等延迟。

上一份报告的写多组在 48 次发布/12 次首屏读中，Pure Pull、Hybrid、Pure Push 分别用了 96、48,048、624,000 条候选写命令。Hybrid 明显回收 Pure Push 写放大，但相对于 Pure Pull 仍以写入、内存和常驻索引换取 Inbox。这个收益需要在反复阅读的大关注图谱中兑现。 [上次逐轮数据](perf-evidence/measured/hybrid-rounds.csv) · [上次报告与次数说明](GoFeed_三亮点最终简历证据验收.md)

对低发布率、粉丝体量较小、活跃粉丝的阅读频率高、读者关注作者较多且预写能安全减少查询来源的作者，Push 更可能值得；对高粉、低读转化或发布密集的作者，写扩散和索引复制更难摊薄。还需要考虑 SLA、冷启动与可见性延迟。上次没有覆盖这些变量的联合分布，本次测的是定向移除空查询的收益上限。固定粉丝双阈值适合作为可解释的工程近似，滞回防止状态抖动。粉丝数不能替代活跃读率或 K，现有测量没有寻找最优分界。

## 五、最终决定与简历影响

**A · 保留当前 Hybrid，不继续二开。** K=500 的 Go/Redis 成本改善真实可复核，说明这笔开销在较大关注列表可观。K=2 的常态中位与成功速率改善有限，K=50 未证明稳定收益。生产选择性读取必须承担迁移、历史与失败语义，还要测新增 MySQL 成本。上次小图谱的数据也不支持将“纯 Pull 更经济”外推到所有目标用户，因此暂不选 B 或 C。

- **亮点一。** 简历可写持久化策略快照、双阈值滞回、高粉写放大和可复核对照。上次高粉单事件的 24,000 → 2 条写命令仍然成立。本次的 K=500 数字适合作为面试中的隔离诊断与方案取舍，不能写成已上线的读取提速，也无需承诺 Hybrid 整体优于 Pure Pull。
- **亮点二。** 可靠点赞沿用既有证据，800 commands/s 仍只用于描述隔离 Worker 输入。
- **亮点三。** 继续披露满页候选可能跳过未索引历史，选择性读取不修复该问题。此处的候选诊断结果不会改变现有 Feed 容量和故障治理结论。
